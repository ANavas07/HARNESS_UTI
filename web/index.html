Las nueve generaciones terminaron en length para medir consumo. No validan calidad, decisiones de agenda ni tool calling. Las rutas con salidas mayores extrapolan estas muestras.
Cómo se derivaron los tiempos

T = N × (1,466418 + salida / 30,722) + tiempo de otras operaciones. Se añadió 25 % de margen y se redondeó hacia arriba a 15 segundos. El tiempo de herramientas es una provisión pendiente de medir. Caché, carga y concurrencia no estuvieron controladas.

04 / Secuencia de implementación

Construir por fases.
Cerrar con evidencia.

El spec define qué construir y cuándo considerar cerrada cada etapa. Los plazos de entrega se acuerdan después de conocer accesos, infraestructura y volumen.

Disponible hoy: documentación, conexión y medidor de Qwen, calculador de rutas y cuatro pruebas de presupuesto. La aplicación de calendario aún debe implementarse.

Stack propuesto

  • TypeScript / Node.js: API, runtime y reglas de negocio.
  • PostgreSQL: calendario, casos, operaciones, memoria y outbox.
  • HTML / CSS / TypeScript: panel y observabilidad.
  • n8n: ingesta de lotes y coordinación; reglas críticas en el servicio.
  • Qwen3-8B-AWQ / vLLM: modelo institucional.
  • Python: scripts de medición ya incorporados.

Decisiones aún necesarias

  • Contrato y autenticación de la API de deserción.
  • Escala y vigencia del riesgo; umbrales de elegibilidad.
  • Asignación de asesores, horarios, buffers y capacidad diaria.
  • Canal institucional de notificación y proveedor.
  • Versión/revisión de vLLM y pesos; tool calling habilitado.
  • Concurrencia, volumen y criterios de aceptación del piloto.

Que funcione.

Verificado

Conexión y consumo

Identidad servida, contexto de 8.192, tokenización, streaming y nueve mediciones sintéticas. Cuatro pruebas del presupuesto pasaron.

Proyectado

Rangos del harness

Presupuestos por ruta y plazos derivados. Falta validar contexto con tools, salidas extensas y carga concurrente.

Por implementar

Flujo de calendario

API de casos, persistencia, reservas, herramientas, canal institucional y evaluación completa A01–A22.

Criterios de aceptación del MVP

Estos son requisitos del spec, no pruebas del calendario ya aprobadas.

Experimento A/B de desarrollo

Misma tarea, mismo modelo, mismos datos y presupuesto. Cambia el paquete de orientación del repositorio.

A · Sin orientaciónvs.B · Con harness
  • AGENTS.md breve, comandos exactos y estructura clara.
  • Fixtures deterministas y evaluación independiente.
  • Cinco pares iniciales en sesiones aisladas.
  • Comparar aceptación, tiempo, tokens e intervención humana.
  • El A/B todavía no se ha ejecutado; las nueve inferencias no lo sustituyen.

Antipatrones que evitamos

  • Instrucciones interminables: una página y enlaces al detalle.
  • Verificación lenta: suite rápida objetivo <60 s; completa en CI.
  • Una tool por endpoint: cuatro intenciones de negocio.
  • Dependencia de una máquina: scripts, prompts, políticas y fixtures versionados, sin secretos.
Revisar el harness en cada retrospectiva y ante fallos de uso, cambios de modelo o crecimiento del contexto.
